# bench/replay — 리플레이 장수·선정 방식 실측

리플레이는 현장 적응 학습(LoRA) 후에도 **기존 능력을 잃지 않게** 하는 장치다.
"몇 장을, 어떻게 뽑을 것인가"를 실측으로 정한 기록이다.

## 측정 구조

실제 라운드 구조를 재현한 대리 벤치다. 두 지표를 함께 본다.

| 지표 | 시험 데이터 | 의미 |
|---|---|---|
| **적응** | 새 도메인 296장 (학습 미사용) | 새 물체를 얼마나 배웠나 ↑ |
| **회귀** | 원 도메인 valid 1,391장 (학습 미사용) | 옛 것을 얼마나 잊었나 ↓ |

모든 조건이 **동일한 새 라벨 20장 · 동일 학습중 검증셋 · 동일 채점셋**을 쓴다
(`--reuse-split-from` 으로 고정). 이게 없으면 K 마다 난수 소비가 달라 표본이 바뀌어
비교가 오염된다. 지표는 COCO mAP@[0.50:0.95].

⚠️ 합성 렌더 도메인에서 재는 **대리 지표**다. 실현장과 같다는 보장은 없지만, 400장을
채택한 근거도 같은 벤치이므로 비교 자체는 공정하다.
⚠️ 전체 mAP는 **소수 클래스의 국소 붕괴를 숨긴다**(2026-08-04 팔레트 전멸 시 mAP 0.96).
배포 판단에는 클래스별 회귀 게이트를 함께 쓴다.

## 결과 (판정 기준: 회귀 Δ ≥ −0.005)

| 리플레이 | 선정 방식 | 적응 | 회귀 Δ | 판정 | 측정일 |
|---|---|---:|---:|---|---|
| **400장** | 무작위 층화 | 0.3423 | **−0.0018** | ✅ | 08-03 |
| 200장 | 무작위 층화 | 0.3463 | −0.0054 | ❌ | 08-03 |
| 200장 | 무작위 층화 (재현) | 0.3391 | −0.0045 | △ | 08-18 |
| 200장 | 큐레이션 | 0.3320 | **−0.0066** | ❌ | 08-18 |
| 1,016장 | 무작위 층화 | 0.3310 | −0.0017 | ✅ (시간 2배) | 08-03 |

**결론: 400장 유지.**

- **적응은 장수와 거의 무관하다**(0.33~0.35). 차이는 오직 회귀에서 난다
- 200장 두 번 측정이 −0.0054 / −0.0045 로 갈렸다 → 이 규모는 **학습 난수로도 흔들린다**
  = 200장은 안전 여유가 없다
- 1,016장은 400장 대비 이득 없이 시간만 2배

## 큐레이션 시도와 실패 (2026-08-18)

"장수를 줄이는 대신 더 잘 뽑으면 되지 않나"를 검증했다.

**방식**(`pick_curated.py`): 학습셋 34,909장의 색·질감으로 이미지별 이상치 점수를 매기고,
현장에 존재하지 않는 극단(합성 원색 등 16.3%)을 제외한 뒤 남은 범위를 5분위 층화.

**결과: 적응 −0.007, 회귀 −0.0021 — 두 지표 모두 무작위보다 나빴다.**

전제가 틀렸다. **"현장에 유용한가"와 "베이스가 기억해야 하는가"는 다른 질문**이다.
현장에 없는 원색 박스도 베이스가 학습한 지식이므로, 리플레이에서 빼면 그만큼 보호받지
못한다. 리플레이의 목적은 후자인데 전자의 기준으로 걸러낸 것이 실패 원인이다.

> 부수 교훈: 처음 구현은 "이상치가 아닌 것 위주"를 그대로 적용해 **점수가 낮은 순으로**
> 뽑았는데, 그러면 전체의 하위 11.9% 에 갇히고 현장 실촬이 0장이 됐다. 리플레이는
> "베이스가 배운 것 **전반**"을 대표해야 하므로 분위 층화가 필요하다. 그렇게 고쳐도
> 무작위보다 나빴다는 것이 위 결과다.

## 실행

```bash
cd <bench 작업폴더>            # 데이터가 큰 관계로 저장소 밖(예: ~/lee3/thirdtask/bench)
# 조건별 라운드 데이터 생성 — valid·새라벨을 고정해야 비교가 성립한다
python3 build_bench_round.py --n-new 20 --k-train 200 --replay-pick stratified \
    --reuse-split-from round_n20_k400/split_manifest.json --out round_A_k200_strat
python3 build_bench_round.py --n-new 20 --k-train 200 --replay-pick curated \
    --reuse-split-from round_n20_k400/split_manifest.json --out round_B_k200_curated
# 학습·채점 (메모리 상한 cgroup 안에서 — 8/3 PC 프리즈 재발 방지)
bash start_ab_capped.sh
```

`pick_curated.py` 는 `build_bench_round.py --replay-pick curated` 가 쓰는 선정 모듈이다.
`~/.cache/eda_model.pkl`(색·질감 군집 모델)이 필요하다.

## 2026-08-21 — 용량 제약으로 200장 결정, 목표를 좁혀 재선정

용량 때문에 200장으로 가기로 정해졌다. 위 표대로 **무작위 200은 기준선을 넘나든다**.
그래서 장수를 줄이는 대신 **지키려는 대상을 좁혔다** — 학습셋 전반 대신
**크래프트 갈색 Carton**. 근거는 EDA(`bench/eda/`): 직접 촬영한 8종 중 크래프트 계열은
학습 Carton 분포 백분위 14~36(한복판), 파란·네이비는 73~99(외곽)다. 현장에서 실제로
만나는 것이 크래프트 계열이다.

### 크래프트의 조작적 정의 (측정)

`~/box_types/` 크래프트 5종 vs 네이비·파랑 3종, 축별 코헨 d.

    b (황청)  +4.82 ★   L (밝기) +4.20 ★   tex_hp −2.30 ★   b_iqr −1.50 ★
    ──── |d| < 1 ────
    size_long +0.85    a +0.61    chroma −0.07  ← 채도는 무용

**밝고 · 노란쪽 · 색이 균일하고 · 표면이 매끈한.** "갈색이니 채도가 높을 것"이라는
직관은 틀렸다 — 네이비도 저채도다.

### 산출물

| 셋 | train/valid | 크래프트 거리 중앙 | Carton 인스(train) | 용량 |
|---|---|---:|---:|---:|
| `replay_kraft200` (보장 유지) | 200/50 | **0.60** | 2,587 | 49MB |
| `replay_kraft200_light` (보장 60%) | 200/50 | 0.79 | **3,381** | 46MB |
| `replay_fixed_v11` (기존) | 400/100 | 1.38 | 2,930 | 153MB |
| 무작위 200 (대조) | — | 1.74 | — | — |

`_light` 의 Carton 인스턴스 3,381 은 **기존 400장 셋(2,930)보다 많다** — 절반 장수로.
거리가 비슷하면 Carton 이 많은 이미지를 먼저 뽑기 때문이다.

```bash
export S=~/eda_work
python3 bench/replay/build_kraft200.py       # 생성 (첫 실행은 소스 스캔 ~10분)
python3 bench/replay/verify_kraft200.py      # 무결성 + 목표 달성 + 부작용
```

시각 비교: `~/replay_kraft200_표본비교.png` — 신규는 무작위 10장이 전부 팔레트 위
크래프트 적재, 기존 400은 빨간 플라스틱 상자·파란 토트·궤도렌더 단품이 섞여 있다.

### valid 은 두 층으로 나눴다

train 과 같은 규칙으로 valid 도 크래프트만 담으면 **경보기가 감시하지 않는 구역**이
생긴다 — 의도적으로 버린 궤도렌더 영역의 드리프트를 못 본다(크래프트 규칙만 쓰면
valid 100장 중 궤도렌더가 1장이었다). valid 의 역할은 망각 탐지이므로 곤란하다.

| 층 | 장수 | 크래프트 거리 중앙 | 뜻 |
|---|---:|---:|---|
| kraft | 37 | 0.62 | 지키려는 대상. **떨어지면 목표 실패** |
| control | 13 | 2.15 | 버린 영역 포함. 하락은 예상되나 **크기는 알아야 한다** |

명단은 각 셋의 `valid_slices.json`. **두 층을 한 mAP 로 합치면 서로를 가린다.**

⚠️ valid 를 100 → 50 으로 줄였으니 **회귀 눈금이 바뀌었다.** 8/18 이전 수치와 직접
비교할 수 없다(Carton 인스턴스 1,327 → 581). 과거와 이어야 하면 기존 valid 100 을
따로 남겨 쓸 것.

### 설계에서 배운 것

- **보장 슬롯을 100% Carton 동반으로 채우면 안 된다.** 슈링크랩 단품 렌더(`render_*`,
  Carton 없음)가 통째로 빠져 기존 셋의 51% → 0% 가 됐다. 그 출처는 베이스 모델이
  슈링크랩을 배운 곳이다 → `--floor-carton-frac 0.6` 으로 40%는 클래스 본래 분포에서.
- **가까운 것부터 자르면 안 된다.** 같은 공개 데이터셋의 비슷한 사진만 쌓인다
  → 적격 풀 안에서 k-medoid.
- 보장 슬롯이 Carton 을 동반하게 고르면 **절반 규모인데 클래스 포함 비율이 오른다**
  (Pallet 34.5% → 65.0%).
- **거리가 비슷하면 Carton 이 많은 이미지를 먼저** 뽑아야 한다. 회귀 측정에서
  인스턴스 수가 곧 표본 크기다 — 이 한 줄로 train Carton 인스턴스가 1,587 → 2,587
  로 올랐다.
- **버그**: 근접/원거리 조각을 앞·뒤에서 잘라 합칠 때 후보가 적으면 겹쳐서 같은 파일을
  두 번 담는다(명단 50 중 고유 46). `take()` 에 이중 담기 방어를 넣었다.
- README 를 손으로 쓰면 재생성할 때마다 숫자가 낡는다 → **빌드 스크립트가 직접 쓴다.**

### ⚠️ 아직 측정하지 않은 것

**이 셋들이 400장보다 낫다는 근거는 없다.** 확인한 것은 "의도한 대로 뽑혔는가"뿐이다.
이전에 다른 목적의 큐레이션이 무작위보다 나빴던 전례가 있다(회귀 −0.0066 vs −0.0045).
채택 전 A/B 필요: ① 기존 400 ② 무작위 200 ③ `replay_kraft200` ④ `_light`.
`config.py` 기본값은 바꾸지 않았다.

또 하나: **궤도렌더 `tm_*` 가 0%** 다(기존 5%). 베이스 Carton 데이터의 53%인 최대
출처인데 크래프트에서 가장 멀어 전부 탈락했다. 의도된 절충이지만, 그 영역에서 LoRA
델타를 붙잡을 것이 없다는 뜻이기도 하다.
